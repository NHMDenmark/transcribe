Two places hold the settings: the file **`.env`** (decided by whoever installs the server; read when the application starts) and the **Settings**, **Languages** and **User levels** pages of the application (decided by its administrators; effective immediately).

After editing `.env` on a server run `sudo -u www-data php artisan optimize:clear` (use the web server user of your system), otherwise the old values stay in the cache.

## The file .env

It is created from `.env.example`. **Never commit it, never send it by e-mail**: it holds the database password and the application key.

| Setting | What it does | Typical value |
|---|---|---|
| `APP_NAME` | Name of the application: the title of the browser tab, and shown in the menu bar while there is no logo | `"Transcription Platform"` |
| `APP_ENV` | `local` on a developer's machine, `production` on a server | `production` |
| `APP_DEBUG` | `true` shows technical errors on the page. **Always `false` on a server**: errors can reveal passwords and paths | `false` |
| `APP_URL` | The public address, **with `https`** when the site is served over https, and with the path if it lives under one. Every link, form and e-mail uses it | `https://transcription.example.org` |
| `APP_KEY` | Encrypts sessions and cookies. Generated by `platform:install`; **if you change it everybody is signed out** | (generated) |
| `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` | The database | |
| `MAIL_MAILER`, `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_ENCRYPTION`, `MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME` | Outgoing e-mail: setting and resetting passwords. **Needed**: accounts created by an administrator have no password until the person sets one from an e-mail link, and without `MAIL_FROM_ADDRESS` that request fails with error 500. Not needed for people who sign in with Google or GitHub | |
| `TRUST_PROXIES` | Leave empty when visitors reach the server directly. `*` (or a list of addresses) behind a reverse proxy | |
| `SESSION_SECURE_COOKIE` | `true` when the site is only served over https | |
| `SESSION_DOMAIN` | Only if the sessions must be shared between sub-domains (`.example.org`) | empty |
| `SESSION_LIFETIME` | Minutes of inactivity before a person is signed out | `120` |
| `FIELD_VIEW_DEFAULT` | How the transcription form is shown when neither the project nor the person has chosen: `all` (every field of a specimen on one screen) or `single` (one field per screen) | `all` |
| `API_URL`, `API_USERNAME`, `API_PASSWORD`, `API_COLLECTION` | The connection to Specify 7, if you sync ([below](#the-connection-to-specify-7)); the last is the default collection | |
| `GOOGLE_*`, `GITHUB_*` | Sign in with those accounts ([below](#sign-in-with-google-or-github)) | |
| `LOG_LEVEL` | How much is written to `storage/logs/laravel.log`: `error` on a server, `debug` while investigating | `error` |

## Settings page

**Admin → Platform → Settings.** The logo and the loading indicator are for *root*; the access for visitors and the creation of accounts are for *root* and *administrators*.

- **Logo.** Shown in the menu bar of every page. Until one is uploaded the name of the application (`APP_NAME`) is shown as text. A transparent PNG, about 40 pixels high, looks best.
- **Loading indicator.** The animation shown while the form looks for suggestions. Optional; a neutral one is used when none is uploaded.

### Access for visitors

Decides what a person can do without an account:

- *Login required* — nothing: every page asks to sign in. This is the default of a new installation.
- *Browse* — read-only pages: the home page, the projects and their specimens, the comments.
- *Submit* — browse, and also transcribe. What an anonymous visitor submits is tied to the browser session instead of to a person, so it is counted but cannot be followed over days.

Choose according to how open the project is meant to be. Open access brings more transcribers, and also more noise: the consensus rule (see [administration.md](administration.md#how-a-value-becomes-valid)) is what keeps the quality.

### Creating accounts

Decides how a person gets an account:

- **Off** (the default of a new installation) — *by invitation*: an administrator creates the account (**Admin → People → Users → new**), or the person signs in with [Google or GitHub](#sign-in-with-google-or-github). The person then sets a password with *Forgot your password?*.
- **On** — a **Register** link appears in the menu for visitors. The person chooses name, e-mail and password, receives a message to **confirm the e-mail address**, and starts at the lowest level, as a plain user; levels rise with validated work and only an administrator changes roles.

Either way **outgoing e-mail must work** ([the file .env](#the-file-env)). Switch it on when the project is open to the public and you want new transcribers to join by themselves; leave it off for a closed group. Turning it off later does not touch the accounts already created.

### Scheduled tasks

Some work is done by the platform itself, without anybody opening a page:

| What | When (server time, UTC) |
|---|---|
| The ranking of contributors of the last week | every day at 00:10 (it is written once per week; the other runs find it done) |
| The progress figures of all projects | every night at 02:00 |
| The submission counts of all contributors | every night at 02:30 |

These figures are also updated when something changes (a submission, an import); the nightly runs are a safety net. All of it is driven by **one cron line on the server** ([how](installation.md#the-scheduler-cron)). This card of the Settings page shows when the scheduler last ran, and a red *Not running* if it did not in the last five minutes: if you see it, the cron line is missing or fails. Until it runs, the weekly ranking on the home page stays empty.

The same card has the **master switch of the automatic sync** and the **time zone of the schedules**: see [Automatic sync](administration.md#automatic-sync).

### Colours

The **colour** of buttons and links is not on this page: it is part of the compiled stylesheet. To use the colours of your institution change `$primary` in `resources/sass/_variables.scss` and run `npm run build`.

## Languages

*Root only.* **Admin → Platform → Languages**.

The interface is written in English, which is also the text shown whenever a translation is missing, so a new installation works with only the English master language it starts with.

To add a language: **Languages → New**, then give

- the **code** (`iso2`): it must be the name of a flag in `public/flags/4x3` (a two-letter country code such as `dk`, `pt`, `de`; the file `dk.svg` is the Danish flag), because the language menu shows that flag. It is also what is stored with every translated text, so choose it once and keep it;
- the **name** as it should appear, in that language (`Dansk`);
- *active*, to show it in the menu.

The new language starts with a copy of the master language's texts. Translating is done on the pages themselves: turn on **edit mode** (the pencil button in the top menu bar, for administrators) and click the small pencil next to any text, in every part of the site: menus, labels, the names and texts of fields and projects, and the website pages and footer. One window shows the text in every language at once.

Texts of the interface that have never been edited have no stored translation; the pencil creates it the first time you save.

## User levels

**Admin → People → User categories.** A level is a name, the number of validated contributions needed to reach it, and its **points**. Transcribers progress automatically by validated contributions. The **points** matter for more than the progress: they are the weight of a person's vote when values are validated (see [administration.md](administration.md#how-a-value-becomes-valid)). A level with *no* number of contributions (the *Validator* level that the installation creates) is never reached automatically: it is given to trusted people by an administrator.

A new person starts at the level that needs the fewest contributions. The names and descriptions can be translated with the pencils.

A **field** and a **specimen** can each require a minimum level, to keep the hard material for experienced transcribers.

## Roles

Roles are not data you edit: they are fixed in the software (`config/roles.php`), and a person has exactly one. The level (above) is something else; it only drives points and progress.

| Role | May |
|---|---|
| **Root** | Everything, including Settings, Languages, and who has which role. The owner of the installation: normally one or two people |
| **Administrator** | Users, fields, projects, the website content (menu, pages, footer), edit the texts, sync, see everything |
| **Project manager** | Manage the projects they created or were given, see the submissions of those projects, resolve conflicts in them |
| **User** | Transcribe |

## Sign in with Google or GitHub

Optional. Create an OAuth application with each provider, with this callback address, and put its identifiers in `.env`:

| | Callback address | `.env` |
|---|---|---|
| Google | `https://<your-address>/auth/google/callback` | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` |
| GitHub | `https://<your-address>/auth/github/callback` | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_REDIRECT_URI` |

The callback address must match what you register with the provider exactly, `https` included. A person who signs in this way gets an account at the starting level.

## The connection to Specify 7

Needed only to send validated data to a collection database. Without it everything else works, and data can be exported (CSV and JSON) from the *Validated values* page.

```
API_URL=https://specify.example.org
API_USERNAME=<a Specify user that may edit the collection>
API_PASSWORD=<its password>
API_COLLECTION=<the id of the Specify collection it logs in to>
```

Specify asks for a collection when a user signs in, so `API_COLLECTION` is the id of the one the platform works in by default (its `id` in the Specify *collection* table). It is only the default: when your projects belong to different collections, set the collection of each project in its form ([how](administration.md#collection-to-sync-into)). Use a dedicated Specify user, not a person's: its permissions are what limits what the platform can change. How fields are mapped to Specify tables, and how a sync is run and checked, is in [administration.md](administration.md#sync-with-specify).
